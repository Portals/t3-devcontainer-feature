# Real-container checks

Run stress checks in this repository's disposable test container. They restart T3 and inject controlled failures; use a separate project container for active chats.

```sh
./test/up.sh
devcontainer exec --workspace-folder "$PWD" bash /workspace/test/check.sh
devcontainer exec --workspace-folder "$PWD" bash /workspace/test/runtime-check.sh no-node
devcontainer exec --workspace-folder "$PWD" bash /workspace/test/server-stress.sh
devcontainer exec --workspace-folder "$PWD" bash /workspace/test/browser-install-stress.sh /usr/local/share/t3-code/install-browser.sh
```

The basic check also executes the image’s official-installer runtime as the development user, even when a newer cached runtime is selected. This catches root-only installation permissions.

The server suite checks unmanaged-port rejection, twenty restart rounds with ten concurrent starts each, identity preservation, HTTP readiness and ten sandboxed Chrome renders. `ROUNDS` can increase the restart count. The browser suite interrupts a real download, runs two concurrent installers, verifies the published browser and renders a page.

For cache-integrity and rollback checks, first update the container to one real release, then another. Both runtimes must exist in its persistent cache. Pass the inactive cached version:

```sh
./update.sh "$PWD" --version FIRST_VERSION
./update.sh "$PWD" --version SECOND_VERSION
devcontainer exec --workspace-folder "$PWD" bash /workspace/test/update-failure-stress.sh FIRST_VERSION
```

This check requires a C compiler and Linux file leases; the default test image provides the compiler. It checks that cached-asset corruption leaves the running server untouched, then uses a real file lease to pause backup after preflight. It removes execute permission from the candidate, modifies a state marker after activation, and verifies that rollback restores the original runtime, state marker and identity. Test file permissions are restored afterward. Successful tests remove their temporary directories; failure logs are retained for diagnosis. Runtime/state recovery backups remain in T3's persistent volume.

For the official runtime installer, pass a real resolved release manifest:

```sh
devcontainer exec --workspace-folder "$PWD" bash /workspace/test/runtime-install-stress.sh /usr/local/share/t3-code/versions.json
```

This interrupts a real archive download, verifies staging cleanup and an unchanged running server, then installs and verifies the release in an isolated temporary directory. It also checks that an inherited release mirror cannot redirect the feature’s download.

The standard Feature CLI scenarios in `test/t3-code-server` cover stable and nightly releases:

```sh
devcontainer features test --project-folder . --features t3-code-server --skip-autogenerated --skip-duplicated
```

The standard CLI scenarios remain available for targeted checks; the automated matrix below runs before publication.

`bash test/published.sh` verifies the exact published GHCR version in a fresh container, including sandboxed browser rendering and runtime updates from a registry-based configuration. It cleans up only its own container and state/home volumes. The release workflow runs it after publishing; **Verify published feature** can rerun it independently.

## Automated matrix

**Test feature** runs on pushes to `main`, pull requests, manual dispatch, and before release. It checks host helpers and all Bash programs (including extensionless commands), then builds Ubuntu 24.04 and Debian 12 on native amd64/arm64 with stable/nightly T3. Separate jobs exercise Node 20 + Java 25, Docker-in-Docker, custom-home UID migration, prebuilt image reuse, old home-volume migration, exact pins, preparation deadlines, changed-version activation, rollback and conservative pruning. Every integration run labels its containers, records a resource manifest, and removes only its own disposable containers and volumes. Manifests are uploaded even after failures.

Run an individual isolated check with Docker and the Dev Container CLI installed:

```sh
node --test test/host.test.mjs
node test/integration.mjs core
node test/integration.mjs contracts
node test/integration.mjs migration
```

Other modes: `uid`, `node-java`, `docker`, `prebuilt`. `T3_TEST_IMAGE` and `T3_TEST_CHANNEL` configure the core check. Migration reproduces the original whole-home persistence contract from `test/fixtures/legacy-persistence.json`, without depending on old Git history or a superseded GHCR release. Host-side orchestration uses Node.js; neither Python nor Node.js is a Feature runtime dependency.

The Docker-in-Docker scenario inherits privileged mode from the official Docker Feature. Ubuntu's AppArmor restrictions can block Chrome's user-namespace sandbox in that mode even though the ordinary T3 container works. That one CI job temporarily permits user namespaces on its dedicated disposable runner and restores its original setting afterward. It still runs Chrome with its sandbox enabled. Local hosts need a compatible AppArmor/user-namespace policy; the Feature does not change host sysctls.
